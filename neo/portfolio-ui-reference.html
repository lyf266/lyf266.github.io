02 / How I work

从问题，到可验证的结果

AI 是工具，不是成果本身。重点是明确问题、设计合适的流程，并检查方案在真实环境下是否成立。

STEP 01

理解场景

谁遇到问题？目前如何解决？真正的限制是什么？

STEP 02

拆解流程

定义输入、规则、异常情况，以及什么才算完成。

STEP 03

实现方案

用合适的代码、API 和 AI 工具完成最小可用版本。

STEP 04

测试与迭代

记录结果、暴露限制，根据反馈修复真正的问题。

04 / About

保持好奇，也尊重证据。

我喜欢从日常学习和工作中的摩擦点出发，尝试用代码、自动化与 AI 做出轻量工具。相比堆叠技术名词，我更希望清楚说明每个项目解决了什么问题、采用了哪些取舍，以及还有哪些地方需要验证。

问题优先先确认真实需求，再决定技术方案。
小步交付先构建最小可用版本，再逐步改进。
结果可核验区分已验证成果、假设和计划。
持续学习通过实践、反馈和复盘拓宽能力。

目标

  • 将现有「窄幅文字目录」改造成 Editorial + 工程案例风格：清楚的标题层级、留白、网格、图标、流程示意和真实产品截图。

  • 保留项目档案完整性。当前站点已有的项目、外链、归档状态及相关内容不能无故删除。示例这里只展现部分项目，需迁移原站的全部内容。

必须保留

  • 中英双语切换、深浅色切换、项目分类筛选、项目展开详情、GitHub / Demo 链接，以及现有的 PDF/打印能力（如 portfolio.pdf 和 portfolio_en.pdf）。
  • 现有 GitHub Pages 地址与可用链接路径；不要未经确认就更换部署方式或引入重型框架。
  • 兼容桌面、平板和手机；支持键盘操作，按钮有明确名称，颜色对比可读，遵循 prefers-reduced-motion。

文案与事实标准

  • 先讲用户遇到的问题和工具带来的实际变化；技术栈放在次级信息层，不把所有项目都写成「AI Agent / Harness / 端到端 / 高杠杆」风格。
  • 避免「彻底免疫、绝不损坏、全面阻断、广播级画质、高置信度」等无边界承诺。描述具体改了什么、在什么环境下验证、还有哪些限制。
  • 性能或节省时间的数据必须有测量口径。没有可复现证据时，删除数值或明确标注为待验证，不得编造用户数、准确率、节省时间或测试结果。
  • 银行考试项目需清楚区分官方公开试题、来源可追溯的题目、基于教材/典型题型编写的模拟题。不能把自编题统称为历年真题。
  • OBS 项目建议表述： “针对特定设备遇到的解码崩溃、透明视频显示异常和场景切换后坐标偏移，调整采集与解码配置并进行回归测试。当前方案针对已复现的问题进行规避和修复，不保证消除所有 USB 传输或驱动故障。”
  • 避免公开不必要的家人健康隐私；相关项目只描述数据整理场景与功能边界。

视觉与交互

  • 用项目流程图表达真实流程，比如 POI「信息源 → 去重/规则评分 → Telegram / Notion」，银行学习工具「模拟答题 → 判分 → 错题复习」，Linux 语音输入「快捷键 → 本地转写 → 插入文字」。不得为了好看而捏造系统组件。
  • 优先展示真实截图；没有截图时可用轻量 SVG/HTML 示意图，不要用与项目无关的图库图像充当产品界面。
  • 图标应语义明确、线条统一；不要每段文案前都放图标。视觉层级应靠排版、留白和对齐建立。
  • 当前页面的项目卡片和案例弹窗是交互示范；可以按现有代码结构选择独立详情页或可访问的折叠面板，但要支持 Escape 关闭、焦点管理与移动端滚动。

交付前验收

  • 检查所有现有项目是否都保留，分类筛选是否覆盖所有条目，中英文状态是否一致。
  • 验证每个 Demo / GitHub / Email / PDF 链接、深浅色模式、手机布局、键盘操作、打印分页及浏览器控制台。
  • 对展示的每个数字标出来源或测试条件；未验证的结果不能写成既成事实。
